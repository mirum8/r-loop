Part 1 Business requirements

Three things are wrong today: a loop a model executes from prose, a pipeline welded to one vendor, and nobody watching a four-hour step that has gone the wrong way. What has to become true is that the driver decides, any agent can do the work, every reviewer you configure reads every phase, and a wrong turn, a wrong plan or a blocked session reaches someone — or is dealt with — before it costs the rest of the night. The twenty-two capabilities below divide between three actors, and the watchdog's four are written last because everything they may do is bounded by what it may never do.

Problem, goals & non-goals

The pack already runs plans to completion, and the loop that does it is prose: 1,057 lines of skills/plan-run/SKILL.md executed by a model that reads the file, decides what the verdict means, decides whether a phase may merge, and ticks the boxes. The measured result is that the loop stops more often than it finishes — the pack's own store holds 8 runs halted at implement-stopped against 4 that finished, across 29 recorded /r:plan-run invocations. Each halt is a context that has to be rebuilt by hand.

The second problem is lock-in. Everything the loop orchestrates is a Claude Code Workflow script, and the Workflow tool exists only inside Claude Code. A plan cannot be built by Codex, by opencode, or by an agent that does not exist yet, however good that agent gets at writing code.

The third is that nothing is watching. A step session is fresh and sees one phase, so an implementation that has gone down the wrong path runs to the end of its four hours and is then reviewed on its merits. Nobody notices that it stopped building what the phase asked for, because noticing needs the whole run in view and every context in the design is deliberately narrow.

Actors

ActorWantsMay authorise
Maintainer a plan built to completion without watching every step, and a clear stop when it cannot be everything — starts the run, answers a paused session, resolves a blocked plan entry, accepts a halt
Provider agent one step's work, in one session, with a prompt and a worktree writing code and tests in its own tree, and committing there; asking the watchdog when it is blocked; never merging, never ticking the plan, never deciding the next step
Watchdog to see the whole run, check each phase before it starts, and stop the run going somewhere wrong three tiers, and the top one is empty: it may veto unilaterally (halt, warn — including a warning that a phase's own fields disagree with what it derives); it may remedy with consent (fix the environment, restart a step, retry differently); it may never approve — not a step, not a landing, not a tick, not even with your consent

The watchdog's third row is the load-bearing one. Consent can authorise an action; it cannot substitute for evidence, and a person clicking yes on a watchdog's summary of a step is strictly worse evidence than the driver's own check of git.

User stories

Maintainer

Run every remaining phase of a plan

As the maintainer, I want to point the driver at a todo.md and have every unticked phase planned, implemented, reviewed and merged in order, so that I do not supervise each step myself.

Given a plan with phases 3–6 unticked and a clean primary tree, when I run r-loop docs/x/todo.md, then phases 3, 4, 5 and 6 are each built and merged in that order, each as one commit carrying its own ticks, and the run reports which phases landed.

Resume a run that stopped

As the maintainer, I want a stopped run to pick up at the step it stopped at, so that a halt costs one step rather than one phase.

Given a run whose implement step for phase 4 failed, when I run r-loop resume, then the driver re-runs phase 4's implement step against the plan the planning step already wrote, and does not re-plan the phase.

See where a run is

As the maintainer, I want the run's shape on screen without opening a session, so that I can tell a working run from a stuck one at a glance.

Given a run in progress, when I look at the TUI, then it shows every phase and its state, the live step with its provider and elapsed time, and any warning the watchdog has raised; and r-loop status --plain prints the same facts as lines for a script.

Choose the agent for each step

As the maintainer, I want planning, implementation and review — and every other session the driver starts: a fallback, a gate fix, the watchdog — each to name their own provider, model and effort, so that I can plan deeply and implement cheaply without one setting governing both.

Given steps.plan.provider: claude and steps.implement.provider: codex, when a phase runs, then the planning session is started with --kind claude and the implement session with --kind codex, and the run banner prints both resolved rows.

Try a different provider for one run

As the maintainer, I want to override a step's provider, model or effort on the command line, so that trying one does not mean editing the project config and putting it back.

Given a config naming claude for implement, when I run r-loop docs/x/todo.md --provider implement=codex --effort implement=high, then implement sessions start as codex at high effort and the banner names each override and the file value it replaced.

Be told when a run halts

As the maintainer, I want a command of my own choosing run when the loop halts or finishes, so that a run that stops at 3am is not discovered in the morning.

Given notify.onHalt set to a shell command, when the run halts, then that command runs with the run summary in its environment, and a non-zero exit from it is logged and changes nothing about the run's own outcome.

Answer an agent's question without leaving the loop

As the maintainer, I want an agent's question to reach me only when the repository cannot answer it, and then in one place — the watchdog's own pane — so that being blocked costs a reply rather than a hunt through workspaces.

Given an implement session that cannot proceed without knowing which module owns a type, when it asks the watchdog, then the step enters waiting-input rather than counting as stalled, its backstop timer pauses, the watchdog answers from the plan or asks me in its own session, and my answer returns to the session that asked; the TUI never asks me anything (ADR-73).

Close a blocking plan decision at startup

As the maintainer, I want the plan's unresolved decisions put to me before the first phase runs, so that a run does not start and then stop on something only I can settle.

Given a todo with an open ## Resolve first entry blocking a phase in the run list, when I start the driver, then the watchdog walks it as /r:plan-unblock does — a brief of why it blocks, the options with their cost and a recommendation, asked in the watchdog's own pane — writes my answer into the plan as a Resolved: stamp the driver commits before phase one is scheduled, and when I say "not now" the driver skips the phases it blocks and the phases that depend on them (ADR-72).

Pre-authorise the blockers worth fixing automatically

As the maintainer, I want to say once which classes of blocker may be fixed without asking me, so that an unattended run is not stopped by a missing dependency.

Given watchdog.allow: [deps, ports], when a step fails because a package was never fetched, then the fix runs without a prompt and is recorded verbatim in the run report; and a remedy outside that list still asks me first.

Stop a run without losing work

As the maintainer, I want to stop the loop while leaving sessions and worktrees in place, so that I can inspect what a step was doing.

Given a live implement session, when I run r-loop abort, then the driver stops scheduling, leaves the session and its worktree standing, names both, and r-loop resume still knows which step was live.

Leave a run to finish on its own

As the maintainer, I want to start a run at night and find it finished — or as far as it could get — in the morning, so that a plan does not wait on me between steps.

Given a six-phase plan started with --unattended, where phase 3's implement session goes quiet and phase 5 depends on phase 3, when the run proceeds, then phase 3 is nudged, fails, is restarted within its budget and, if it still fails, is blocked together with phase 5 while phases 4 and 6 land; an agent's question the repository cannot answer is taken by the watchdog on the agent's own recommendation, citing the line that supports it; and the report opens with the number of times a person was needed and every decision the driver took on its own.

Override the prompts for this project

As the maintainer, I want this project's review prompt to differ from the shipped one, so that a repo with its own rubric does not have to fork the driver.

Given .r-loop/prompts/review.md in the repo, when a review step runs, then that file is rendered instead of the shipped one, and the banner names which file it used.

Add a provider the driver has never seen

As the maintainer, I want to run a step on an agent the driver does not ship support for, so that adopting a new one is a config edit.

Given a providers.pdev block naming a herdr kind, the model and effort flags, the completion signal and, if it has one, its native review command, when a step names provider: pdev, then the session starts on that agent and no driver code mentions it.

Add a step to every phase

As the maintainer, I want to add a step to each phase — a security pass, a docs update — without changing the driver, so that the pipeline fits this project rather than the one it shipped for.

Given .r-loop/config.yaml listing a step docs after implement, with its own prompt, provider row and the shipped evidence check diff, when a phase runs, then a docs session opens after the implement step, is judged by the same two-signal rule as every other step, and the banner lists the phase's pipeline as plan → implement → docs → land.

Review each phase with every configured reviewer

As the maintainer, I want each phase's plan and each phase's code read by every reviewer I configure, round after round, and only the findings that are verified, real and severe fixed, so that the review is as wide as the reviewers I have and the fix is no wider than the problems that exist.

Given steps.implement.reviewers naming claude and rounds: 3, when the implement session writes its sentinel and its diff passes, then a reviewer pane opens to the right of it in the same workspace, runs /code-review report-only and writes a findings file; the implement session checks every finding against the code, gives it a verdict and a severity, dismisses one only with a path:line that shows it wrong, and fixes only those real at P1 or P2; a fresh reviewer then looks again, until a round is clean or the third round ends; the step's work is committed once, after that; and the report lists each finding with its round and verdict.

Provider agent

Report a step's outcome so the driver can act

As a provider agent, I want one documented way to say how my step ended, so that the driver never has to read my terminal to find out.

Given a step prompt carrying a sentinel path, when I finish or halt, then I write the outcome to that path as my last action, and the driver reads it rather than my output.

Ask the watchdog a question

As a provider agent, I want one way to ask when the plan does not tell me something I need, so that guessing is never the cheapest option available to me.

Given the driver's ask_watchdog tool in my session, when I call it with a question, its options and my recommendation, then the call blocks until the watchdog answers — from the repository, or from the maintainer it asked in its own session — and I am not penalised for the wait; I never ask the person in my own pane.

Fan out reviewers using my own mechanism

As a provider agent, I want the reviewer list expanded into whatever parallel mechanism I actually have, so that one prompt works on every agent.

Given a review prompt containing {{agent:logic}} and {{agent:tests}}, when it is rendered for my provider, then those expand to my own parallel-agent call, or — when I have none — to a sequential list that the run report names as a degradation.

Watchdog

Halt a step that has gone the wrong way

As the watchdog, I want to stop a running step the moment it stops doing what its phase asked for, so that a wrong path costs minutes rather than its full four hours.

Given an implement session whose output shows it redesigning a subsystem the phase never mentioned, when I confirm against git that the diff agrees with what I read, then the step is stopped, its session is left standing, the run halts, and my reason is recorded in the run report.

Fix what is blocking a step

As the watchdog, I want to repair the mundane thing stopping a step and start it again, so that a missing dependency does not cost a person a halt.

Given a step failing because a toolchain is absent, when the remedy class is pre-authorised — or I ask and am told yes — then the exact command I proposed is run and recorded verbatim, the step restarts in a fresh session, and nothing about the plan or the code has been touched.

Answer from the whole run's context

As the watchdog, I want the first look at an agent's question, so that anything the plan already answers does not reach a person at all.

Given a question whose answer is in the spec, the tech-design or an earlier phase, when it arrives, then I answer it with a file:line citation and the answer is logged; and when I cannot cite an answer, I ask the maintainer in my own session and answer with the citation maintainer — or, in an unattended run, take the agent's recommended option, citing the line that supports it.

Check a phase before it runs

As the watchdog, I want to read each phase before its first step, so that a phase whose own fields are wrong is flagged before four hours are spent on it.

Given a phase whose Files: names two packages, when I read the phase and the tree and derive that a third package must change, then a warning naming the disagreement appears in the TUI and the run report before the planning session opens, and the phase still runs.

The v1 line

v1 ships twenty of the twenty-two: everything that makes a run survivable, everything that keeps a person out of it unnecessarily, and all four watchdog capabilities — because a watchdog that can see but not act is the version that produces warnings nobody can do anything with. What waits is everything that widens the loop rather than closing it.

The line falls there because everything deferred assumes the loop already works. Waves need a serial loop that finishes; a second source needs the phase contract proven; a third-party provider needs the adapter shape settled by the two that exist; and drift-watching needs enough completed runs to tell a quiet watchdog from a blind one. Shipping any of them first would be widening a loop nobody has run to the end.

Adding a step ships in v1 even though it widens the pipeline, because it costs almost nothing once the three shipped steps are themselves entries in a list rather than three hard-wired calls — and that list is what keeps the loop from being edited every time a project wants one more pass (ADR-45). The phase check ships for the opposite reason: it closes the loop rather than widening it, and it costs one read per phase in a pane that is already open (ADR-53).

Part 2 Domain

The driver owns a run, its steps, the sessions they run in, and the traffic that flows back — questions, signals, remedies. Everything about the work itself is produced elsewhere and only read: a step is asked to produce an artifact, and the repository is asked whether it did. A review round is the one time a step has several agents at once — reviewers beside the step's own session, reading and never writing — and a phase is checked by the watchdog before its first step. Making a question an explicit state is what lets the rest be strict — silence now means a session that has gone quiet without asking for anything, which is a narrow and genuinely suspicious thing.

Domain model

Two vocabularies meet here and are easy to confuse, so they are separated once and used consistently everywhere below. The todo is the phased plan file /r:spec-design writes — docs/<topic>/todo.md, a sequence of ### Phase N blocks. The phase plan is .task-plans/<slug>.md, written by one phase's planning step and consumed by its implement step. The driver reads the first and never writes it except to tick; it causes the second to be written and never writes it either.

Lifecycles

Three things move through states, and two of a Step's are deliberately not terminal. waiting-input is a session that has asked something and is waiting for an answer — its backstop timer is paused, because a step must never be killed for asking. stalled is what is left once questions are explicit: a session that has gone quiet with no signal at all, which is a much narrower and more suspicious thing than it used to be.

Invariants

Two signals, never one. When a step session writes its sentinel, if the evidence that step owes is not present in git or on disk, the driver records the step as failed, per step; on violation the run halts naming the step and the missing evidence, and nothing is merged. The evidence differs by kind: a planning step owes a phase plan file with a status: planned header and its four sections, written by that step, and no change beyond it; an implement step owes a change since it started; each review round owes a verdict for every finding. Source: the pack's own fan-out rule — a sentinel can be written by a run that then failed to commit. Configurable: no.

A merge is never made on an unproven phase. When a phase's last step reports ok, if the phase's Done when: command does not exit 0 in the primary tree within its timeout (land.gateTimeout, default 30 minutes), the driver performs no merge and no tick, per phase; on violation the run halts with the command's output. A phase whose block carries no Done when: line is a named skip recorded in the run report, never a silent pass. Source: 33 recorded /r:task-review runs returned build: "n/a", 31 of them over trees carrying 42k added lines. Configurable: no.

One live step per run. When the driver is asked to spawn a step, if a session for another step of this run is already live, it refuses and exits non-zero, per run; on violation nothing is spawned and the existing session is named. A review round is the one place several agents are live at once: the reviewers open in panes beside the step's own session, in its workspace, and none of them writes (ADR-56). Source: the serial design — two writers in one run would write the same worktree. Configurable: no in v1; the cap becomes steps.fanout.maxUnits when waves land.

Code and ticks land as one commit. When a phase lands, if the merge commit does not carry both the phase's code and its ticked checkboxes, the driver refuses the landing, per phase; on violation it halts before touching the todo. Source: "built" and "ticked" must revert together. Configurable: no.

The driver keeps the rules; the watchdog keeps the judgement. Every step state, landing, tick, commit and run-list change is made by the driver's code. The watchdog is a full session that decides and edits where a duty names it — today, the ## Resolve first section — and the driver checks its edit and commits it. A step's own signals from the watchdog are still veto (halt, warn) and remedy only: a signal that would mark a step ok or lift a halt is rejected and recorded. Source: some work cannot be done by rule, and an LLM that can only veto could not do it (ADR-71, which replaced the invariant "the watchdog never approves"). Configurable: no.

A remedy is authorised before it runs, and recorded verbatim after. When the watchdog proposes a remedy, if its class is not in watchdog.allow and the maintainer has not answered yes, no command runs, per remedy; on violation nothing is executed and the refusal is recorded. The exact command as proposed — not a summary of it — is what is authorised and what is written to the run report. Source: the watchdog can never approve its own action, so the allow-list lives in the driver. Configurable: the allow-list, yes; the rule, no.

A question never kills a step. When a step enters waiting-input, its backstop timer is paused for as long as the question is open, per step; on violation — that is, if a step in that state is ever killed by a timer — the run halts rather than discarding the question. The question waits with the watchdog for as long as that takes, and the driver never answers it itself: a watchdog that is gone when a step asks, or goes while it holds a question, halts the run instead (ADR-73). Source: a step killed for asking teaches every future step to guess instead. Configurable: no.

Nothing is built on a failed phase. When a phase is blocked — its step failed past its remedies, a watchdog halted it, or its gate stayed red — if a later phase depends on it, directly or through others, the driver does not start that phase, per run; on violation nothing of the dependent phase is spawned and the block is named. Phases that do not depend on it still run and land (ADR-65). Source: a phase built on a failed one leaves the plan half applied with nothing recording which half. Configurable: no.

Every configured reviewer reads every step it reviews. When a review round starts, if any reviewer named in the step's reviewers cannot be started — its pane fails to open, or its provider declares no native reviewer — the driver records the step failed, per step; on violation the run halts naming the reviewer, and the step's session is not asked to judge anything. Source: a review that silently ran with fewer readers reads exactly like one that ran with all of them. Configurable: the list, yes; the rule, no.

Every finding gets a verdict. When the step's session writes its sentinel after a review round, if the verdict record does not carry a verdict — real, not real, out of scope — and a severity for every finding the round's reviewers wrote, or a not-real verdict carries no path:line that exists, the driver records the step failed, per step; on violation the run halts naming the first finding without one. Source: the pack measures roughly a third of code-quality findings as dismissed at triage, a dismissal has to be visible to be checked, and the agent judging the findings is the one that did the work (ADR-56). Configurable: no.

Nothing is committed before its review completes. When a step's session writes a sentinel, if the phase branch has moved since the step started, the driver records the step failed, per step; on violation the run halts naming the step. The driver itself commits a step's work exactly once, when its last review round ends ok, and a step that ends any other way leaves its work uncommitted with a recorded snapshot (ADR-58). Source: the maintainer, round 20 — unreviewed work on the branch is one merge away from landing. Configurable: no.

Key flows

Eight flows, four of which end badly. The first is drawn because it contains the branch the others are variations of.

A step fails

The session writes a failure sentinel, or writes an ok sentinel with no evidence behind it. The driver records the step failed and holds it for the remedy window, in which the watchdog may restart it — within watchdog.maxRestarts. If it is not restarted, the phase is blocked: its worktree — with the step's work uncommitted and a snapshot of it recorded — and its session are left in place, notify.onWarn fires, and every phase that depends on it is skipped. The run goes on with the phases that do not. When nothing is left to run it halts, runs notify.onHalt, and prints the r-loop resume that picks up every blocked phase at its stopped step (ADR-65).

A step asks a question

The session calls ask_watchdog. The step enters waiting-input, its backstop pauses, and the driver hands the question to the watchdog. If the watchdog can answer it from the spec, the tech-design or an earlier phase, it answers with a file:line citation; the answer is logged and returned to the session, which resumes. If it cannot cite an answer, it asks the maintainer in its own session — with its question tool, rewritten so it makes sense without the agent's context — and answers with the citation maintainer. An empty or invalid citation is refused and the question stays with the watchdog; the TUI never shows it. An --unattended watchdog never asks: it takes the agent's recommended option, citing the line that supports it. If the watchdog is gone when the step asks, or goes while it holds the question, the driver halts the run with the watchdog is gone; the question stays unanswered, and r-loop resume starts a new watchdog (ADR-73).

A step stalls

herdr reports the agent blocked, idle or done, no sentinel exists, and no question is open. That combination is much narrower than it was before questions became explicit, and it is genuinely suspicious: a session that has gone quiet without asking for anything. The driver sends it one fixed nudge — write the sentinel if you are done, ask or fail if you are blocked — because most such sessions finished and never wrote it. If the agent starts working again the step carries on; if it is still quiet a grace period later, the step fails, and the failure takes the path above. The session is never closed — it is both the evidence and the place to intervene (ADR-62).

The watchdog stops a step

Reading the running session's output, the watchdog sees the implementer redesigning a subsystem the phase never mentions. It confirms against git that the diff agrees with what it read — session output is narration, and a halt is not called on narration alone. It then emits a halt signal: the step is stopped, its session is left standing, the run halts, notify.onHalt fires, and its reason is written to the run report. A wrong call here costs one r-loop resume, which is the whole reason it is allowed to make the call at all.

A blocker is fixed and the step restarts

A step fails because a toolchain is missing. The watchdog diagnoses it and proposes an exact command. If the remedy's class is in watchdog.allow, the driver authorises it immediately; otherwise the watchdog asks the maintainer in its own session and proposes again with their reply as maintainer_said. On yes, the watchdog runs the command it proposed, the driver records it verbatim, and the step restarts in a fresh session — on the same prompt, or with an addendum naming what was learned, so the retry differs from the repeat. Nothing about the plan or the code has been touched.

The driver dies mid-run

The machine reboots, or the terminal is closed. RunState is in .r-loop/ inside the repository, so it survives both. r-loop resume reads the last recorded step and re-runs it; a phase whose planning step completed is not re-planned unless the maintainer passes --replan (ADR-60). A dirty worktree is claimed when it matches the last snapshot recorded for that step, since a step's work stays uncommitted until its review ends; a step killed during a review round resumes at that round. The one case it refuses is a worktree holding changes no snapshot recorded — that tree is neither safe to build on nor safe to discard, and the run stops for a person.

The watchdog checks a phase

Before a phase's first step, the driver hands the watchdog the phase block and the tree. The watchdog derives which files must change and how deep the cut is, compares that with the phase's Files: and Risk:, and when they disagree emits a warn signal naming the difference. The warning shows in the TUI and lands in the report; the planning session opens regardless. It cannot halt on this, and it cannot rewrite the fields (ADR-53). The watchdog is always on (ADR-71).

A step is reviewed

The plan or implement session writes its sentinel and its evidence passes; nothing is committed. The driver snapshots the worktree and splits one pane per configured reviewer to the right of the step's session, in the same workspace — codex runs /review on claude's plan, claude runs /code-review on codex's code — each report-only, each writing the findings file the driver named. While they work, the step's session waits and its clocks stand still. The driver then checks that no reviewer changed the tree and prompts the step's own session, which still holds everything it did: check each finding against the code, give it a verdict and a severity, dismiss one only with a path:line, fix only those real at P1 or P2, write the verdict record. A fresh reviewer then looks again, handed the earlier findings and verdicts, until a round finds nothing real or the step's round limit is reached — the limit is a warning, never a halt. Only then does the driver commit the step, once (ADR-56, ADR-57, ADR-58).

Part 3 Architectural characteristics

Three things are being bought, and each has a number: no loop approval made by a model, two independent signals before a step counts as done, and five places the driver grows without its loop being edited. The first is phrased by direction rather than by actor, and that phrasing is what lets a watchdog exist at all — it may push the run toward stopping, never toward proceeding. What is being spent is speed, tokens, and the review depth the pack's own pipelines measure.

Part 5 Architectural style

One control process sequences the work; every unit of real work runs in a separate process it starts, watches and never links against. It is also a small server, which is the one thing the pattern does not give you — workers need a way back in, and confining that to two named MCP surfaces is what keeps the first characteristic checkable. Inside the binary the code is hexagonal: a core that holds the loop and its rules and imports nothing from herdr, git, MCP or the terminal, and adapters around it behind small ports. One self-contained binary in a herdr pane, no daemon, nothing split into a service, nothing read from the skill-pack.

The style

A supervisor over out-of-process workers. One control process owns the sequence and the state; every unit of real work runs in a separate process the supervisor starts, observes and never links against. The phase is a pipeline inside that supervisor, and the stages hand off through the filesystem rather than through memory.

The supervisor is also a small server, which is the one thing that does not follow from the pattern. Workers need a way back in — to ask the watchdog a question, and for the watchdog, to signal and answer — so the driver exposes two MCP surfaces: ask_watchdog to every step session, and the signal, remedy and answer tools to the watchdog alone. Scoping them separately is not a detail: an ordinary step session that could emit a halt signal would be a worker vetoing its own supervisor.

Inside the binary, a hexagonal core (ADR-46). The loop, the step and phase state machines, the two-signal rule, the rejection of forward-moving signals and the remedy allow-list live in a core that imports no adapter. Everything that touches the outside world is an adapter behind a port the core defines: the plan file, the session host, git, the run state on disk, the config file, the prompts, the MCP server, the face (TUI or --plain) and the notify hooks. The core is tested with fakes for every port and no real herdr, git or terminal. A port is shaped by what the core needs from its one adapter today, not by a guess at the second (ADR-47).

Against the three driving characteristics:

  • Determinism — the supervisor is the only thing that branches, and it is code. A worker returns an artifact and a sentinel; it never returns a decision.
  • Evidence over autonomy — an out-of-process worker cannot hand back a typed object, so the hand-off is necessarily something the supervisor can verify independently. The constraint that looks like a limitation is what makes the two-signal rule natural rather than bolted on.
  • Extensibility — a worker is a process with a prompt, which is the largest interface every candidate agent already implements, and MCP is the same argument for the channel back. Inside the binary, the hexagon is what makes the other four seams cheap: a step kind and a check register with the core, and a source or a host is an adapter behind a port the core already has.

The styles rejected

  • In-process orchestration — what the pack does today with Workflow scripts. Ruled out by portability across agents: the mechanism exists only inside one vendor's CLI (ADR-4).
  • Embedding an agent SDK as a library — ruled out by determinism, and by cost: it puts the loop back inside a model's context, and the subscription rules make non-interactive API-billed runs a separate pool.
  • A daemon with an HTTP API and a dashboard — ruled out by proportionality. One maintainer on one machine, and herdr already renders every session.
  • A headless driver with an attachable client — the shape that would let a run survive any terminal. Ruled out by proportionality again: the driver runs in a herdr pane, which already survives the window closing, and splitting it would buy an IPC boundary and a daemon lifecycle for that one property (ADR-30).

Topology

One binary, in a herdr pane. The driver renders the TUI on the left and opens the watchdog, rloop-wd-<runID>, beside it by splitting its own pane (HERDR_PANE_ID) with herdr pane split — or, started outside a herdr pane, in a workspace of its own that closes with the run; every step session gets its own workspace, and a step's reviewers open as panes inside it. A step's workspace stays standing while its phase is blocked, and closes when a later attempt of the step starts or the phase lands; a landed phase's worktree and branch are removed after it. It runs for the length of the run and exits with it, creating no daemon: the sessions belong to herdr's server, which is running anyway, and the worktrees belong to git. A run started in a plain terminal instead dies with that terminal — the pane is what makes it survivable, and that is a documented instruction rather than something the driver enforces.

Self-contained. The binary carries its own default config and prompts and parses the plan file itself; it reads nothing from the skill-pack and needs no script interpreter (ADR-43). The one thing the two share is the todo.md format that /r:spec-design writes. In a project it owns one directory, .r-loop/, whose committed half is the project's config and prompt overrides and whose ignored half is run state and worktrees (ADR-49).

Three things outside the process survive it, and that is deliberate — each is what a resume reads: .r-loop/ in the repository, the phase branches and worktrees, and the herdr workspaces. Nothing is split into a service, because nothing here has a different scaling profile, a different release cadence or a different blast radius; it is one sequence over one repository.

Part 6 Decisions

Seventy-four decisions, each with the alternative that was live at the time; ten are superseded and kept in place, and thirty carry a later amendment. Six carry most of the weight: dropping the Claude Code Workflows, which buys portability and costs the measured review depth; running every configured provider's own reviewer at once and fixing only what a judge marks real, which buys part of it back; making a provider a config block rather than driver code; performing the landing in code; the split that gives every rule to the driver and every judgement to an always-on watchdog (ADR-71, which replaced the three-tier rule); and the phase check that lets the same watchdog warn about a plan before four hours are spent on it. Ten record the move to a repository of its own — self-contained, a hexagonal core, and a phase pipeline made of step kinds — and the rest largely follow from those. ADR-53 to ADR-55 were made in a review of decisions earlier rounds had taken by default, ADR-56 to ADR-60, in round 20, redesign the plan step and move review into every step, the next seven, in round 21, make a run finish with nobody present, ADR-68 gives every session the driver starts its own model and effort, ADR-69 and ADR-70 let a run take an issues file and gate each of its items on tests the item proves it needs, ADR-71 and ADR-72 make the watchdog the run's LLM and give it the ## Resolve first walk, ADR-73 lets step agents ask only the watchdog and only the watchdog ask the maintainer, in its own session, and ADR-74 buys back the UI check as a named reviewer that runs the project's /test-app.

ADR-1 — The loop runs as a terminal CLI, outside every agent session

Status accepted

Context Determinism (Part 3) asks that no loop decision be made by a model. A loop hosted inside an agent session is executed by that model by construction, and the harness caps a single blocking call at 600 s — shorter than one implement step.

Decision The driver is a binary run from a shell pane; it starts sessions and outlives none of them.

Alternatives A skill that launches a detached driver — rejected, the orchestrating session then sits idle and a crashed driver is reported by nobody. Hardening the in-session prose loop — rejected, the context still grows per phase and the loop is still text a model follows.

Consequences The loop becomes testable and stoppable, and gains nothing from Claude Code's permissions, hooks or trust model — which it must therefore arrange itself for the sessions it opens. A second entry point exists beside /r:plan-run.

Revisit when a single blocking harness call can exceed one implement step's duration.

ADR-2 — One session per step, not one per phase

Status accepted · amended by ADR-56 — a step's session stays live through its review rounds and applies their findings

Context Long agent sessions degrade as context fills; the pack's own fan-out gives a whole phase to one session. Choose the agent for each step (Part 1) also requires a session-level boundary, because a provider is chosen when a session starts.

Decision Plan and implement each get their own fresh session; review, once a step of its own, is now a half of each (ADR-56).

Alternatives One session per phase, as fanout.sh runs today — rejected, it offers no place to select a provider per step and carries one context across all three.

Consequences Every hand-off must go through disk, which is what makes the two-signal rule implementable; and three sessions re-read context that one would have held.

Revisit when the per-step context re-read measurably exceeds the cost of the degradation it avoids.

ADR-3 — The driver is an alternative to /r:plan-run, not a replacement

Status accepted

Context /r:plan-run works, is measured, and owns the concurrent path. Replacing it would put an unproven loop in front of the only one that has finished a plan.

Decision Nothing existing is migrated or edited; the driver is a new front door.

Alternatives Replace --herdr and reduce fanout.sh to the driver's spawn layer — rejected by the maintainer, who asked that existing skills keep working.

Consequences Two loop encodings exist, which the pack elsewhere treats as a lockstep tax; here they are deliberately not kept in lockstep, because they are different designs rather than two copies of one.

Revisit when the driver has run a full plan end to end twice without a halt the prose loop would have avoided.

ADR-4 — No Claude Code Workflows: the driver owns every step prompt

Status accepted · amended by ADR-74 — the UI track comes back as a reviewer running the project's /test-app

Context Portability across agents is a driving characteristic. Both pipelines the pack orchestrates are Workflow scripts, and that tool exists only inside Claude Code, so any step built on one can never run on Codex, opencode or an agent that does not exist yet.

Decision The driver ships its own prompt per step and calls no Workflow script and no bundled agent.

Alternatives Keep both Workflows and make only the planning step provider-agnostic — rejected: it leaves the two most expensive steps locked to one vendor, which is the lock-in the project exists to remove. A one-argument edit to task-run-implement.workflow.js so the planning half could stop early — rejected for the same reason once the goal was stated.

Consequences This is the decision that costs the most. The driver gives up the explorer fan-out, the UI/UX design phase, the Codex plan review with its two triage lanes, the domain-sliced implementers, and /r:task-review's roughly fifteen tracks with their recorded verdicts — including the measurements those tracks produce (code-quality 944 confirmed against 391 dismissed; end-verify 74 against 1). A single prompt per step does not reproduce them, and this document does not claim it does. Running each provider's own native reviewer (ADR-23) buys part of it back — those are real tools rather than prose imitations of one — but only part. What it buys is that every step can run on any agent.

Revisit when the review step's fixes per run falls below what /r:task-review records for the same repository.

ADR-5 — Fan-out is templated in the prompt and expanded per provider

Status superseded by ADR-54 — the driver opens one workspace per reviewer itself; no prompt carries a placeholder and no provider declares a fan-out capability

Context ADR-4 removes the pack's fan-out, and a review by one reader is materially narrower. Providers do have their own parallel mechanisms, but no two share an API.

Decision Prompts carry {{agent:<name>}}; PromptRenderer expands it into the resolved provider's own mechanism.

Alternatives One agent per step doing the whole job — rejected, the review becomes a single reader on every provider. The driver spawning N sessions per step and joining them — rejected for v1, it needs a join protocol per step and rebuilds what fanout.sh already does.

Consequences Some review breadth survives the loss of the Workflows, and every provider must now declare a fan-out capability — which creates the failure ADR-8 exists to make visible.

Revisit when two providers in use both declare fanout: none.

ADR-6 — A provider is a config block, not driver code

Status accepted · amended by ADR-54 — the block declares a native review command where it has one, and no fan-out capability

Context Portability across agents sets the target at one config block and zero driver lines. herdr already supports 23 agent kinds, so the driver cannot ship a branch per agent and stay honest about the claim.

Decision providers.<name> declares the herdr kind, the model and effort flag shapes, the completion signal and the fan-out capability. The driver reads it and names nothing.

Alternatives A small shipped adapter file per provider — rejected: it can carry real logic rather than strings, but adopting an agent then means editing the pack instead of the project's own config.

Consequences Adding an agent is a config edit, and a wrong block fails at spawn time rather than at load time — so the registry must validate what it can and say which field it could not.

Revisit when a provider needs behaviour that cannot be expressed as flags and a signal.

ADR-7 — Prompts ship with the pack and are overridden per project

Status superseded in part by ADR-43 and ADR-49 — the shipped prompts are embedded in the binary rather than living in the pack, and the override is .r-loop/prompts/<name>.md; the decision to ship defaults and let a project override them stands

Context Override the prompts for this project (Part 1): a repo with its own review rubric should not fork the pack to get it.

Decision Templates live in the pack; a file of the same name under the project's .config/loop-prompts/ replaces it, and the banner names which was used.

Alternatives Shipped only, edited in the repo — rejected, it makes any per-project rubric a fork.

Consequences Two places to look when a run behaves oddly, which the banner is there to collapse to one.

Revisit when more than half of the projects using the driver override the same template — that is a shipped prompt that is wrong.

ADR-8 — fanout: none is a named degradation, never a silent one

Status superseded by ADR-54 — there is no fan-out capability left to degrade; the rule it protected survives as the invariant that every configured reviewer reads every step it reviews

Context A review that collapses to one reader produces a report that looks exactly like a review that fanned out. The pack has the same failure recorded elsewhere: a blocked track written into findings reads as 100% precision.

Decision A provider declaring fanout: none gets the reviewer list sequentially, and the degradation is written to the step log and the run report.

Alternatives Silently render the sequential form — rejected, it is indistinguishable from the full one. This was decided rather than discussed; the alternative is named because it is the behaviour every other design here would have produced by default.

Consequences The run report gains a field that is usually empty, and a phase can land with a review the report describes as narrower than intended.

Revisit when the report's degradation field is never read.

ADR-9 — Landing runs in driver code, never in a session

Status accepted

Context The merge is the irreversible step, and determinism puts exactly those decisions in code.

Decision LandGate runs the gate command, merges, ticks and commits directly.

Alternatives A fourth session running /r:plan-run's finish prose — rejected, it hands the one unrecoverable operation to a model and costs a session per phase.

Consequences A merge conflict halts the run for a person, and ticking needs a script rather than an instruction.

Revisit when conflicts at the land step become common enough to want a resolving agent.

ADR-32 — The watchdog may veto unilaterally, remedy with consent, and never approve

Status accepted · the "never approve" tier superseded by ADR-71 — the watchdog is a full session; veto and remedy on a step stay as written

Context A watchdog with the whole run in view is the only thing that can catch an implementation going somewhere wrong — every other context in the design is one phase wide. But determinism of approval (Part 3) is the characteristic everything else rests on.

Decision Three tiers. Veto — halt and warn — is unilateral. Remedy — fix the environment, restart a step, retry with an addendum, retry on another provider — requires consent. Approve — a step marked done, a landing, a tick — is never permitted, with or without consent.

Alternatives Veto only, with no remedies — rejected in the round after it was decided: a watchdog that can see a missing dependency and not fix it produces warnings nobody can act on. No watchdog at all — rejected, nothing else can see across phases.

Consequences The asymmetry is what makes this safe: a model wrong about an approval lets bad work land and nothing downstream re-reads it, while a model wrong about a veto costs one r-loop resume. The third tier stays absolute even under consent, because a person clicking yes on a watchdog's summary is worse evidence than the driver's own check of git. Enforcement lives in Watch, not in the watchdog's prompt.

Revisit when a rejected signal turns out to have been right more than once.

ADR-46 — Inside the binary: a hexagonal core, with ports and adapters

ADR-53 — The watchdog checks each phase before it runs, and may only warn

Status accepted · supersedes ADR-12

Context A phase's Files: and Risk: are written by /r:spec-design from the spec, before any code exists, and by phase five the tree may no longer match them. ADR-12 chose to trust them as written; in the decision review the maintainer chose an agent that verifies each phase instead. Check a phase before it runs (Part 1) and determinism of approval (Part 3) bound what that agent may do.

Decision Before a phase's first step, the watchdog reads the phase block and the tree, derives which files must change and how deep the cut is, and emits a warn Signal naming any disagreement with the plan. The phase runs regardless.

Alternatives No verifier, as ADR-12 stood — rejected by the maintainer. A separate pre-plan step kind in a fresh session, the recommended shape — rejected by the maintainer: one more session per phase for a job the watchdog's context already covers. One pass over every phase at run start — rejected: verdicts on late phases go stale as earlier ones land. Halting the phase on a mismatch — rejected: a false mismatch stops an unattended run until a person resumes it. Rewriting the plan's fields — rejected: a second writer to the plan file, and the driver's own checks would then trust values a model wrote.

Consequences The watchdog pane must be up before phase one; it always is, since --no-watchdog was removed (ADR-71). A wrong plan still runs, with a warning in the TUI and the report. The check is judgement rather than a mechanical rule (ADR-33), so its threshold lives in the watchdog's prompt with the rest.

ADR-54 — The review is the driver's own fan-out: one workspace per reviewer, then one session to judge and fix

Status accepted · supersedes ADR-5 and ADR-8 · amends ADR-23 and ADR-24 · amended by ADR-56 — the reviewers open as panes inside the step they review, and the step's own session judges and fixes

Context ADR-5 put reviewer placeholders in the prompt and let each provider expand them its own way, and ADR-8 named the degradation when a provider had no way. In the decision review the maintainer chose a different shape, in these words: run one claude workspace with /code-review and one codex workspace with /review; they do not fix anything; they return a findings list; then judgement and fix of the relevant and real ones, P1 and P2 only. Review each phase with every configured reviewer (Part 1) and evidence over autonomy (Part 3).

Decision steps.review.reviewers lists providers. SessionManager opens one workspace per entry at once on the phase branch; each runs its provider's native reviewer report-only and writes a findings file. When every file exists, a fix session on the implement row (ADR-25) gives every finding a verdict and a severity, fixes only those it marks real at P1 or P2, and records the verdicts.

Alternatives Placeholders expanded per provider (ADR-5) — superseded: it depends on each provider's own parallel mechanism, which no two share and some lack. Driver workspaces only as the fallback for a provider with no mechanism, the recommended shape — rejected by the maintainer: two fan-out paths to keep working. One reviewer per phase — rejected: a single reader on every provider.

Consequences The review is exactly as wide as the reviewer list and depends on no provider's fan-out. The driver gains its only concurrency in v1 — read-only workspaces over one branch — and a join. The findings formats differ by provider, so the fix session reads each file as written, with its reviewer named. A reviewer that cannot start fails the step rather than narrowing the review. The placeholders and the fanout capability leave the prompts and the config.

ADR-56 — Review is a half of every step: reviewer panes beside the step's session, which verifies and applies

Status accepted · supersedes ADR-24 and ADR-25 · amends ADR-2, ADR-23, ADR-45 and ADR-54

Context ADR-54 made review a step of its own: one workspace per reviewer, then a fresh fix session on the implement row. It could not review a plan, and the fixer had to rebuild the intent behind a diff it did not write. In round 20 the maintainer asked for the review of plans and code alike, with the reviewer opened "on the right near the main pane of workspace" and "the same plan/implementation pane" verifying and applying the findings; a reviewer never fixes, and only findings that are verified and relevant are fixed. A plan is the cheapest place to correct a mistake — the pack's Codex plan review has 281 confirmed plan defects on record. Evidence over autonomy (Part 3).

Decision Any step row may carry reviewers, rounds and reviewTimeout. After a step's work half passes its evidence check, one pane per reviewer is split to the right of the step's own pane, in the same workspace; each runs its provider's native reviewer report-only and writes a findings file. The step's own session — the agent that did the work — then gives every finding a verdict and a severity, dismisses one only with a path:line that shows it wrong, fixes only those real at P1 or P2, and writes the verdict record. The default pipeline is plan → implement, with codex reviewing claude's plan and claude reviewing codex's code.

Alternatives Keep review as its own step (ADR-54) — rejected: it cannot review a plan, and it pays a fresh fixer to re-derive what the author already holds. A fresh fix session in the step's workspace — rejected by the maintainer: verifying a finding needs the reasons behind the choice it is about. A reviewer that fixes the plan in place — rejected by the maintainer: findings are verified before anything changes.

Consequences The agent judging the findings did the work, so it has a stake in dismissing them: a dismissal must cite code that exists, and every dismissal is in the run report with its citation. The review step, its row, the fix row and the reviewed phase state leave the design. A step's session outlives its first sentinel and takes a second prompt per round. The review is still exactly as wide as the reviewer list, and a reviewer that cannot start still fails the step.

Revisit when a step's session dismisses more than half of one reviewer's findings across three runs, or a dismissed finding is later confirmed real.

ADR-57 — Review runs in rounds up to a configurable limit, with a fresh reviewer each round

Status accepted

Context The maintainer asked for rounds with configurable limits. A fix can introduce what a second look would catch, and a reviewer that has read its own findings tends to confirm they were fixed rather than look again.

Decision rounds per step row — 2 for plan, 3 for implement by default, 0 to turn review off — and reviewTimeout per round, covering the reviewers and the fix pass together. A round is clean when its reviewers report nothing or its verdicts hold nothing real at P1 or P2, and a clean round ends the review. Each round starts a fresh reviewer agent in a fresh pane in the same place, handed every earlier round's findings and verdicts and the change since the last round; a finding dismissed with evidence is not raised again without new evidence. The step's own session stays the same across rounds. Reaching the limit after a round that fixed something is a warning — its last fixes are unreviewed — never a halt.

Alternatives One reviewer session across rounds — rejected: it anchors on its own findings and its context grows every round. Halting at the limit — rejected: every real P1 or P2 is already fixed by rule, so a halt stops an unattended run over work that is probably fine; a per-row onLimit: fail waits for a need. A full re-review with no memory of earlier rounds — rejected: it re-raises what was dismissed.

Consequences A step costs at most rounds × (reviewers + one fix pass) beyond its work half. The step's stall clock and backstop stand still while its reviewers work. A round pays a few seconds of agent start-up.

Revisit when rounds regularly reach the limit, or no second round finds anything across five runs.

ADR-58 — A step's work is committed once, after its review

Status accepted · amends ADR-16 and the 2026-09-18 choice that the driver commits a step's leftover files after every sentinel · amended 2026-09-19 — evidence is measured from the tree before the step's first attempt, after a resumed attempt that found its earlier attempt's complete plan on disk was failed for changing nothing

Context The maintainer's rule: nothing is committed before review completion. Without commits the driver still needs to know where a round started — to prove a fix changed its file, that a reviewer changed nothing, and whose files a stopped run left behind.

Decision The driver commits a step's work once, when the step ends ok after its last round; an agent never commits, and a moved branch fails the step. Where the driver needs a point in time it takes a snapshot — the worktree written to a git tree object through a throwaway index, touching no branch — and records it before the round or the terminal state it marks. A step that fails leaves its work uncommitted, with its snapshot recorded.

Alternatives Commit after every sentinel and squash at the end — rejected: unreviewed work would sit on the branch. No snapshots, with weaker checks — offered and not taken: every round would re-read everything, a "fixed" claim could not be proved, and a resume could not tell a step's leftovers from someone else's.

Consequences One commit per step on the phase branch, and nothing unreviewed ever reaches it. A resume claims a dirty worktree that matches the last recorded snapshot and refuses anything else (ADR-16). Evidence measures a step's own change from the baseline — the snapshot taken before the step's first attempt, recorded in the run directory before that attempt spawns — so a re-run over its own earlier attempt's leftovers, by restart or by resume, is judged on the step's cumulative change, and complete work whose attempt failed passes on retry. A new attempt of a step that already ended ok (a --replan, a later gate fix) takes a fresh baseline, so committed work and another step's leftovers never count as its change.

Revisit when a snapshot claim wrongly accepts or refuses a tree.

ADR-59 — The plan step writes a four-section phase plan, judged by code

Status accepted · amends ADR-51

Context The planning step owed "a plan file with a status: header", which an empty file satisfies. Research in round 20: the providers' own plan modes are mostly prompts, block the sentinel write and end in an approval dialog nobody answers; Codex's plan template asks for a plan with no open decisions and its assumptions recorded; ralphex and Ralph write a plan file with fixed sections. The maintainer asked for something functional but not overcomplicated, and said the pack's /r:task-run is not the reference.

Decision The plan step is an ordinary session with a driver-owned prompt: read the code before deciding, look up what the repository can answer, ask or record what it cannot, write, check. The plan is status: planned and four sections — Summary, Changes, Tests, Assumptions. The plan-file check requires the header, the four headings, a non-empty Tests section, and a change touching nothing but the plan. The phase check's warnings go into the prompt; the plan's assumptions go to the TUI and the report.

Alternatives A provider's plan mode — rejected: it blocks the sentinel and stalls on approval. The /r:task-run plan format with a linter that resolves every citation and maps every criterion to a named test — rejected for v1 as more machinery than a phase needs; it is the first upgrade if plans prove thin. Only the status: header — rejected: an empty plan passes.

Consequences r-loop's phase plans are its own format; they stay in .task-plans/, but /r:task-run does not adopt them, and ADR-51's promise that either loop picks up the other's plan is withdrawn. Plan quality rests on the prompt and on the plan's review rounds, not on the check.

Revisit when implement fails because its plan was thin or wrong twice in one run.

ADR-60 — A wrong plan can be replanned on resume

Status accepted · amends ADR-16

Context A phase whose planning step ended ok is never re-planned, so an implement step that fails because its plan is wrong is retried against the same plan on every resume.

Decision r-loop resume --replan re-runs the phase's plan step as a new attempt, with the stopped step's reason as its addendum, and then the stopped step. It is the maintainer's choice — never the driver's and never the watchdog's.

Alternatives Re-plan automatically when implement fails naming the plan — rejected: an agent's claim that its plan is wrong would then decide the next step. Let the watchdog restart the plan step — rejected: a restart applies to a failed or stalled step, and the plan step ended ok.

Consequences The plan's commit stays on the branch; the new attempt edits the plan on top of it and of the stopped step's uncommitted work, and goes through its own review rounds.

Revisit when most resumes use --replan, which would argue for an automatic path.

ADR-61 — --unattended is a mode: routine remedies pre-authorised, restarts bounded, every automatic decision reported first

Status accepted · amends ADR-13 and ADR-37

Context In round 21 the maintainer asked that the loop be "as unattended as possible". Finishing a plan with nobody present had been a non-goal; it becomes a goal, measured as fewer than one halt that needs a person per run. The watchdog could already remedy and restart, but only with consent, and the allow-list ships empty (ADR-37) — so an unattended run stopped at its first routine failure.

Decision --unattended adds unattended.allow — deps, ports, locks, restart, retry, provider by default — to watchdog.allow for the run. Every step, in every mode, has at most watchdog.maxRestarts restarts (default 2). Every person's answer, consent and resume is recorded as a human touch; the report opens with their count and an Automatic decisions section — nudges, restarts, fallbacks, gate-fix rounds, round-limit warnings, blocked and skipped phases. Without the flag nothing about consent changes.

Alternatives Make unattended the default — rejected: a run the maintainer is watching should ask, and the empty allow-list is what keeps a first run honest. Automatic retry in the driver, without the watchdog — rejected: a retry that repeats a deterministic failure pays for a second session (ADR-13); the watchdog's diagnosis is what makes a restart differ from the repeat.

Consequences The driver still authorises every remedy from a list in config and the watchdog still approves nothing, so determinism of approval holds. An unattended run can do more before a person sees it, which is why the report puts those decisions first.

Revisit when an automatic decision listed in a report is one the maintainer would have refused, or unattended runs still need a person more than once a run.

ADR-62 — A stalled step is nudged once, then fails

Status accepted · amends ADR-14 · amended 2026-09-19 — the nudge offers the ask tool only to a session that has an ask channel · amended by ADR-73 — the tool it names is ask_watchdog

Context ADR-14 left a stalled step standing and the run paused until a person came. Since questions became explicit (ADR-29), a stall is an agent that went quiet without asking — most often one that finished and never wrote its sentinel, or one sitting at a prompt of its own.

Decision After watchdog.stallGrace of quiet, the driver sends the agent one fixed nudge — write the sentinel if you are done; ask, or write a failed sentinel, if you are blocked. Working again, the step carries on; still quiet a grace period later, it fails with stalled: no response to nudge and takes the failure path, remedies included. The session is never closed. The nudge is text in the driver's code, never a model's.

Alternatives Keep pausing (ADR-14) — rejected: every stall then costs a person. Let the watchdog write to the session — rejected: the watchdog reads sessions and never writes one, and a fixed sentence needs no judgement. Kill and re-run — rejected as before: the session is the evidence.

Consequences A stall costs at most two grace periods before the loop moves on. A run's exit code is 3 when its first block began as a stall.

Revisit when a nudged agent does something other than write its sentinel, ask or fail.

ADR-63 — With --unattended, an unanswered question resolves to the agent's own recommendation

Status superseded by ADR-73 · was accepted · amends ADR-29

Context A question the watchdog cannot cite waits for the maintainer for as long as that takes (ADR-29, ADR-39). At night that is the whole night, for one sentence.

Decision ask_user takes an optional recommended option. With --unattended, a question still open unattended.questionTimeout (default 30 min) after it reached the maintainer is answered by the driver: proceed with your recommendation — or, with none given, with the option you judge safest, named in your sentinel's reason. The answer is recorded as given by timeout and listed as an automatic decision.

Alternatives Let the watchdog answer without a citation — rejected: the citation is what keeps a model's answer checkable (ADR-39). Fail the step at the timeout — rejected: the question was about the agent's own work, and failing it costs the phase for a choice the agent had already weighed.

Consequences The agent decides a detail of its own work, which is what it would have done without the tool; the decision is visible, and the step's evidence and review rounds still judge the result. Evidence over autonomy gains its one stated exception.

Revisit when a timed-out recommendation is the cause of a blocked phase or a follow-up fix.

ADR-64 — A red land gate gets a bounded fix round before the phase is blocked

Status accepted · amends ADR-10 · amended by ADR-68 — land.fix may name the gate-fix step's own provider, model and effort; absent, it is the implement row

Context The gate re-runs a phase's Done when: over the merged tree (ADR-10). When it fails, the cause is usually small — a test the phase broke elsewhere, a lint rule — and the output says what.

Decision A red gate aborts the merge as before. With land.fixRounds left (default 1), a gatefix step runs in the phase worktree on the implement row, with the command and its output, reviewed for one round, committed once; the landing then starts again from the merge. A gate still red, or a gate-fix step that does not end ok, blocks the phase.

Alternatives Block at once — rejected: it spends a person on what an agent can read off the output. Let the landing session fix it in the primary tree — rejected: the primary tree is never an agent's workspace (ADR-9).

Consequences No merge is ever made on a red gate — the rule is untouched. A phase can cost one more session and one more review round at the end.

Revisit when gate-fix rounds weaken tests to pass, or never succeed.

ADR-65 — A halt blocks only the failed phase and the phases that depend on it

Status accepted · amends ADR-13

Context ADR-13 halted the whole run on a failed step because a phase built on a failed one leaves the plan half applied. Every phase already states what it builds on in Depends on:, and /r:spec-design checks those edges; a phase that does not depend on the failed one is not built on it.

Decision A failed step, a watchdog halt, a merge conflict or a red gate blocks its phase. Every phase that depends on it, directly or through others, is skipped. The loop continues, in order, with the phases that can run; when none is left the run halts with the exit code of its first block, and resume re-runs every blocked phase from its stopped step. Abort still stops everything at once.

Alternatives Halt the run, as before — rejected: one failure at midnight leaves every independent phase unbuilt. Continue with every later phase — rejected: it builds on the failure.

Consequences Phases land out of the order a halted run would have landed them, so a blocked phase resumed later may meet a merge conflict with work that landed meanwhile; that is a conflict halt like any other. The rule rests on the Depends on: edges being right, which the watchdog's phase check helps catch.

Revisit when a phase that landed past a block turns out to have depended on it without saying so.

ADR-66 — A step row names a fallback provider

Status accepted · amended by ADR-68 — fallback may be a block naming its own model and effort · amended 2026-09-19 — a --provider <step>=<p> naming that row's fallback provider swaps the fallback for the run to the row's configured provider, model and effort (the values before any flag), shown on the banner with provenance flag:--provider, rather than exiting 2; a config file fallback naming its row's own provider is still rejected

Decision A step row may name fallback, a provider — codex for plan and claude for implement by default, each on its own default model and effort. Under an allow-listed provider class a restart may name only that fallback; any other provider still asks.

Alternatives Let an allow-listed restart name any provider — rejected: the watchdog would be choosing the agent, which is a setting. Detect limits in the driver by parsing provider output — rejected: output formats are the provider's, and reading them is the watchdog's job.

ADR-67 — An answer can come from any shell

Status superseded by ADR-73 — r-loop answer is removed · was accepted · amended 2026-09-19 — the answer file is published by hard link, so a second r-loop answer for a question whose first answer is still waiting is refused, exit 2 · amended 2026-09-19 — when a step ends, its open questions are withdrawn: recorded as answered by withdrawn, taken off the face, and the agent's pending call released; a question arriving for an ended step is withdrawn at once, and an answer to a withdrawn or ended step's question is dropped with a note — never delivered, never a human touch, never moving a step out of ok or failed — after a late answer was found reviving a failed step

Context A question reaches the TUI, or stdin in --plain. A maintainer away from the pane — told by notify.onWarn on a phone — had no way to answer short of reaching that terminal.

Decision r-loop answer <id> <text> writes the answer to a file in the run directory; the loop reads that directory every tick, and the first answer — from the face or a file — wins. r-loop status lists open questions with their ids.

Alternatives A network endpoint on the driver — rejected: the driver serves only loopback MCP, and a file needs no port, token or client. Answering inside the agent's pane — rejected: the driver would not see the answer, so it could not record it.

ADR-68 — Every session the driver starts names its own model and effort

Status accepted · amends ADR-20, ADR-64 and ADR-66 · amended 2026-09-19 — --provider touches the fallback in one case: naming the fallback's own provider swaps the two (ADR-66); --model and --effort still touch only the row's own keys

Context Steps and reviewers each carry provider, model and effort (ADR-20, ADR-56). Four sessions did not: a fallback ran on its provider's defaults, a gate fix inherited the implement row whole, the watchdog had a model and no effort, and the command line could swap a step's provider but not its model or effort. Each is a place a maintainer pays for depth they did not choose, or cannot buy depth they want. herdr passes everything after -- to the agent, so each is a pair of flags the provider block already knows how to spell (ADR-6).

Revisit when a role needs a setting that is not provider, model or effort.

ADR-69 — An issues file is a second source: one item is one phase

Status accepted · amends ADR-21

Context /r:issues-draft writes issues-<slug>-<date>.md and /r:issues-fix reads it, or any hand-written backlog in the same grammar. The file has no ### Phase headings and, by design, no Depends on:, Files: or Done when:: one line per item, the sender's number and words, and acceptance criteria indented beneath. The maintainer wants the driver to run such a file as it runs a plan.

Decision A file with no ### Phase heading is read as an issues file, in the grammar /r:issues-fix reads: a column-0 - [ ], * [ ], - or 1. line with the lines indented under it, or a ##/### heading followed by prose; everything before the first item is a header. An item is done when it is ticked, struck through, carries <!-- fixed: … -->, or sits under a Done, Completed, Fixed, Shipped or Archive heading. Each item is one phase, numbered by its place among all items, done or not, so numbers hold as items are ticked and new ones are appended; each indented criterion is one of the phase's items, so the plan step must test every one. Landing ticks the item's own line and appends <!-- fixed: r-loop/phase-N -->, which /r:issues-fix reads as done. Items have no dependencies and no Files:, so the checks scoped by Files: stay quiet for them. A file named *-notes.md is refused (exit 2): it is the draft's reply to the sender, and its headings would read as items. An item with no indented criteria runs on its title alone, and the dry run and the banner warn about it. When the only uncommitted paths are the backlog and its notes file, the refusal of a dirty tree says to commit them.

Alternatives Port the /r:issues-fix verifier and group items into phases — rejected, as in ADR-12: the verifier derives what the plan step already derives, and a group of items is one landing that can fail for any one of them. Require the issues format to grow Files: and Done when: — rejected: the drafter writes from a message before anyone has read the code, and a stale hint is worse than none.

Consequences One more parser beside the plan reader, behind the same port. A long backlog is a long serial run.

Revisit when two items of one backlog keep conflicting on land, or a follow-up message is appended to a backlog while a run is on it — the next landing's commit takes those lines with it.

ADR-70 — An issues item lands on its own tests, red at base, and on the discovered suite

Status accepted · amends ADR-10 and ADR-48

Context An issues item has no Done when:, so under ADR-48 a whole backlog would land without a single test being run. A gate command written in config was rejected by the maintainer: projects span stacks, and the command would have to be kept by hand in each one.

Decision Two gates, both run by the driver, never taken on an agent's word. The suite: before the first item lands, a gate session in the primary tree finds the command that builds the project and runs its whole test suite, and writes it in backticks to gate.md in the run directory; the driver runs it on the base and accepts it only if it passes there, records it as a gate-discovered event, and every later landing and every resume reuses it. The item: the plan step of an issues item writes a ## Gate section with one command that runs only the item's new tests, and the plan-file check refuses a plan without it. At land the driver checks the phase adds or changes a test file, copies those tests onto a worktree of the base and runs the item command there — it must fail, or the tests do not exercise the change — and then, after the merge, runs the item command and the suite joined by &&. A red result goes to the gate-fix rounds of ADR-64; no suite, no plan or no ## Gate blocks the phase with a named reason. A todo.md phase keeps its own Done when:, or the named skip. Stale items: when the code already does what the item asks, or the item is not code work, the plan step writes status: already-done or status: not-work with a ## Evidence section citing a path:line per criterion; the plan reviewers open the citations like any other plan content, and the driver then reports the item as item-skipped, without landing or ticking it, and the run goes on. Coverage: the reviewers of an item's plan and implement steps name the test for each criterion and report every criterion no test proves as a finding.

Alternatives A gate: key in config — rejected by the maintainer: one more thing to write per project. Guessing the command from the build files — rejected: wrong wherever a project runs its tests its own way, and the failure would look like the item's. Letting the plan step choose the only gate — rejected: the agent would choose its own judge; the red-at-base run is what keeps the item command honest.

Consequences One more session per run and one extra suite run on the base; each landing runs the item tests twice and the suite once. A project whose suite is red on the base cannot run a backlog until it is fixed, and the halt says so.

Revisit when a discovered suite proves wrong in a run, or a red-at-base run refuses tests a human would accept.

ADR-71 — The driver is deterministic; the watchdog is the run's LLM

Status accepted · supersedes the "never approve" tier of ADR-32 and the invariant "The watchdog never approves" · amends ADR-53 · amended by ADR-73 — its one-channel paragraph is replaced: step agents ask the watchdog, and the watchdog asks the maintainer in its own session; watchdog.fallback is removed

Context Some run-wide work cannot be done by rule: briefing a blocker, judging whether a plan drifted, answering an agent's question. The watchdog is the one session that is open for the whole run and holds the plan, the spec and what it watched. The three-tier rule kept it to veto and remedy, so a blocker was put to the maintainer as a bare prompt that took any text as the answer — and "abort", typed to leave that prompt, was stamped into a plan as a decision.

Decision Two halves. The driver is deterministic: the TUI, the phase loop, the evidence checks, every commit and the run list. The watchdog is the run's LLM: a full session that reads, runs commands, asks the maintainer in its own session and edits the files a duty names; the driver checks the edit and commits it. Only the watchdog asks the maintainer, in its own session (ADR-73), written for someone who has not read the logs: a step's question stays with the watchdog until it answers from a path:line or asks the maintainer and answers with the citation maintainer; a remedy off the allow-list, or a provider that is not the row's fallback, is authorised only by maintainer_said, the maintainer's reply, quoted. The watchdog is always on: --no-watchdog is removed, and a watchdog that cannot start on its provider refuses the run with exit 4, with no retry on another provider. Its row defaults to claude / opus / high. Signals about a step stay veto and remedy only. Milestone reports and the backlog suite command keep their dedicated sessions.

Alternatives A dedicated session per judgement — rejected: each one starts cold and reads again what the watchdog already holds. Keep the watchdog veto-only and put the judgement in the driver — rejected: the judgement cannot be written as a rule. Let the watchdog run the loop through MCP or a CLI — deferred: nothing needs it yet, and the plan file is a narrower channel the driver already reads and checks.

Consequences A run always costs one standing session at opus/high. Test harnesses fake the watchdog instead of turning it off. Loop management by the watchdog is a named non-goal.

Revisit when a run needs the watchdog to change the loop in a way the plan file cannot carry.

ADR-72 — The watchdog walks ## Resolve first

Status accepted · supersedes ADR-42

Context /r:plan-unblock closes blockers well: it sorts each entry as a decision or a person's, briefs why it blocks with options and their cost, asks with a recommendation, and stamps the answer with what settled it. ADR-42 asked the same entry as raw text with a free answer.

Decision Before the first phase, the driver sorts every open entry that blocks the run list — decision, person or unclassified, by resolve_scope.py's patterns ported to Go, a person's first and an unmatched entry treated as a person's — and sends them to the watchdog with each blocked phase's block, then waits for the watchdog's done file (unblock.done in the run directory), up to watchdog.unblockTimeout; the prompt returning is not the walk finishing, since it returns as soon as the watchdog starts asking the maintainer. The walk aims to fix each blocker, not only to record it: the watchdog asks "how do we fix it?", offering the work it can do itself (measure, try, read, decide from the code) beside the maintainer's own choices, an estimate to go on with, and "not now"; an entry of kind person gets only "I do it myself" and "not now". It walks them one at a time: a brief in Simplified Technical English, asked in the watchdog's own session with the options recommended first plus "I don't know" and "Not now", only "Confirmed done" or "Not now" for a person's entry, and the answer written into the section as a tick with Resolved:, Alternative: and Outstanding: lines. The driver then refuses any change outside ## Resolve first (undoing it) or outside the plan file, makes one commit docs: resolve N plan blockers, and skips the phases an entry still open blocks, with the phases that depend on them. --unattended skips the walk and those phases. A stop during the walk halts the run with exit 4.

Alternatives Keep the driver's own prompt and add options — rejected: the options and the recommendation need a reading of the repository. Refuse the run while an entry is open — rejected: "not now" is a real answer, and the phases it does not block can still run.

Consequences The first phase starts a few minutes later when a plan has open blockers. A skipped entry stays open and is asked again by the next run that includes its phases.

Revisit when a walk's stamp disagrees with what the maintainer chose.

ADR-73 — Step agents ask the watchdog; only the watchdog asks the maintainer, in its own session

Status accepted · supersedes ADR-63, ADR-67 and the one-channel paragraph of ADR-71 · amends ADR-28, ADR-29, ADR-38, ADR-39 and ADR-62

Context The maintainer talks to the watchdog in its pane, and the watchdog asked them through ask_user, which put the question in the TUI's questions panel — a second place to answer, beside the conversation the question came from. A question the watchdog could not cite also escalated to that panel as the agent wrote it, and r-loop answer was a third way in.

Decision Step and reviewer sessions keep one MCP tool, ask_watchdog(question, options?, recommended?) → answer; the step still enters waiting-input with its backstop paused, and the driver hands the question to the watchdog. The watchdog answers with answer_question(id, answer, citation): a path:line in the primary tree, or maintainer when it asked the maintainer in its own session — with its question tool (AskUserQuestion) when it has one, otherwise as plain text. An empty or invalid citation is refused and the question stays with the watchdog. The watchdog's surface has no ask tool. Consent is the maintainer's reply, quoted: propose_remedy(…, maintainer_said?) and restart_step(…, maintainer_said?); off the allow-list, an empty quote comes back ask. The TUI's questions panel, Face.Ask, r-loop answer, watchdog.answerWindow and unattended.questionTimeout are removed. The driver never answers a question itself: a watchdog that is gone when a step asks, or goes while it holds a question, halts the run with a driver signal the watchdog is gone, and r-loop resume starts a new one. With --unattended the watchdog never asks: it answers from the repository or takes the agent's recommended option, citing the path:line that supports it. watchdog.fallback is removed too: a watchdog that does not start on its own row blocks the run with exit 4.

Alternatives Remove the step channel and have agents fail with the question in their sentinel reason — rejected: a failed step costs its session and a restart for a one-line answer. Keep the TUI panel as a fallback when the watchdog is gone — rejected: two places to answer is the problem, and a run without its watchdog has lost its judgement anyway. A driver answer ("take your recommendation") when the watchdog is gone — rejected: the driver would be making the call a model is there to make.

Consequences The maintainer answers in one conversation that already holds the run's context, and every answer that reaches an agent carries a citation or the word maintainer. A run cannot survive its watchdog: losing it halts the phase that asked. An unattended run's answers rest on the watchdog's reading of the repository, which the report lists under Questions with who answered.

Revisit when the maintainer wants to answer from somewhere other than the watchdog's pane, or a halt for a gone watchdog costs more than the answer would have.

Amendment Every session r-loop starts needs ask: mcp: a step, fallback, reviewer or gate-fix session on ask: none would be told to call ask_watchdog and not have it. Preflight refuses such a provider in any role with exit 2, <field>: provider <name> has no MCP ask channel, and restart_step refuses such a provider with the same reason, consent or not; this supersedes ADR-40.

ADR-74 — The UI test is a named reviewer on implement, gated on the project's test-app skill

Status accepted · amends ADR-23 and ADR-4

Context Dropping the Workflows (ADR-4) lost /r:task-review's UI track: deploy the app, drive what the diff changed through the project's own /test-app skill, and look at how it renders — three viewports for a web page, three geometries for a terminal UI. The native reviewers (ADR-23) read the diff and never run the app, so a phase can land with a broken page and a clean review. A reviewer was one provider running its native command, so a second Claude reviewer beside the Claude code reviewer could not exist.

Decision A reviewer block takes three more keys: name (its identity in agent, files and events, default the provider), prompt (its template, default review; any other needs no native command) and requires (a repository path). The embedded implement row adds {name: ui, provider: claude, model: opus, effort: high, prompt: review-ui, requires: .claude/skills/test-app/SKILL.md}. Before its first round the driver looks the path up in the step's worktree, then in the primary tree; absent from both, the reviewer sits the step out and a reviewer-skipped event says so. The agent, not the driver, judges whether the diff touches anything the app renders, prints or accepts; with nothing, it reports no findings. It runs /test-app, which deploys and tears down by itself, and reports through the same findings file, verdict, fix half and rounds as a code reviewer.

Alternatives A ui step kind after implement — rejected: it is the first step that produces no artifact, so no shipped check can judge it, and it would fix its own findings outside the verdict rules. A path pattern in the driver deciding whether the diff is UI — rejected: it misses terminal UIs and puts a judgement in the deterministic core. Filing real P3/P4 UI findings to an issues file, as /r:task-review does — rejected for now: the run report already lists them.

Consequences A project with a test-app skill gets a runtime and visual check in every implement round at the cost of a deploy per round; a project without one loses nothing and its report names the gap. The ui reviewer's findings can reopen a round like any other, and the gate fix, which inherits implement's reviewers, runs it too.

Revisit when a deploy per round costs more than the defects it catches, or the pack's test-app contract changes its surface marker.

Part 7 Technical details

Go renders it, herdr hosts the sessions, git holds the evidence, and MCP is the way back in. One block-style YAML file per project carries everything tunable — the phase pipeline, the per-step rows, the reviewer list, the providers, the watchdog's allow-list and the notification hooks — over defaults built into the binary. The prompts are the product here, as they are in the skill-pack, and the watchdog's is the one carrying the most judgement, now including the phase check. The binary needs nothing but Go to build and nothing from the skill-pack to run.

Adding a step is a pipeline entry and a steps row with its own prompt — a docs pass after implement, judged by check: diff and reviewed or not as its row says, needs no Go. A provider used in every project can live in ~/.config/r-loop/providers/<name>.yaml instead of in each project's file.

The MCP surfaces. Every step session and every reviewer session gets one tool, each on its own URL: ask_watchdog(question, options?, recommended?) → answer, which blocks until the watchdog answers; the driver hands the watchdog question <id> from phase-<N>/<kind>: <text> options: … recommended: …. The watchdog session gets its own tools, offered to no other session, and no ask tool — it asks the maintainer in its own session (ADR-73): signal(kind: warn|halt, step, reason, evidence), propose_remedy(class, command, why, maintainer_said?) → {decision: authorised|refused|ask, reason}, restart_step(step, addendum?, provider?, maintainer_said?), and answer_question(id, answer, citation), whose citation is a path:line in the primary tree or maintainer; an empty or invalid one is refused and the question stays open. A signal whose effect would move the run forward is rejected by Watch and the rejection is recorded — the tool surface is narrow by design, but the enforcement is not the surface. A signal whose step is not phase-<N>/<kind> goes through Watch too, is rejected, and halts the run.

Prompts are embedded in the binary — plan, implement, review, fix, milestone, gatefix and watchdog — each replaceable by a file of the same name under .r-loop/prompts/. A template receives the phase block, the plan path, the branch, the sentinel path and the acceptance criteria. The plan prompt asks for the four-section plan (ADR-59) and carries the phase check's warnings; the review prompt goes to every reviewer pane, names the round, that reviewer's findings path and the earlier rounds' files; the fix prompt goes to the reviewed step's own session with every findings file of the round; the watchdog prompt carries the phase check beside the rest of its judgement.

Rollout

r-loop is a new repository, but the skill-pack is touched, so this section stays — short.

  • Expand. The repository r-loop holds this document, the visual identity (DESIGN.md) and, later, the code. The skill-pack loses the same files and gains one note in its CLAUDE.md naming the todo.md format as a contract with a second tool and .task-plans/ as a folder both write to, in their own formats (ADR-43, ADR-51, ADR-59). No skill, workflow or script in the pack changes (ADR-3).
  • Migrate. Nothing is migrated. The two loops coexist and are chosen per run by which command is typed.
  • Contract. There is no contraction step in v1, and the criterion for considering one is in ADR-3's revisit line.
  • Rollback. Remove the binary, and .r-loop/ from the projects that ran it. The point of no return is per run rather than per install: once a phase has landed, its merge commit is ordinary history and removing the tool does not remove the code. A remedy the watchdog ran against the environment is not rolled back either — it is recorded, not reversible.
